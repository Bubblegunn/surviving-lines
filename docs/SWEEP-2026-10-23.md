# surviving-lines 0.3.0 real-repository sweep

Tool: /private/tmp/r13/ours-src-head/bin/surviving-lines.js (not edited). Node v24.13.0, git 2.50.1 (Apple), macOS. No model calls.
The sweep was stopped early at the request of another agent in the session; all 57 planned full clones were finished, but the special cases below are only partly covered (see "Not covered").

## Method and conventions

- 57 full clones (all under 60 s each) plus 5 special local repos (see below). Pinned commits are the HEAD of the default branch at clone time (table).
- Per repo, three CLI runs (`-q --json`): default; `--merge-identities`; and a "raw" run with `--keep-generated --no-detect-reformat --include-bots`, which removes the tool's own exclusions so it can be compared to plain git.
- Reference (scripts/ref.py): `git blame --line-porcelain -w -M [-C] [--ignore-revs-file]` over regular, non-binary files (binary = `git ls-files --eol` says `i/-text`; symlinks and gitlinks skipped), summed per lowercase `author-mail`. Convention used, as documented by the tool: blank lines dropped (JS `trim()` semantics) and also reported with blank lines; `-C` on only when file count <= 2000; the repo's `.git-blame-ignore-revs` passed when present (plus the tool's own `blame.autoIgnoredRevs`, which were empty in raw mode); commits = non-merge commits, `%aE` (mailmap applied), lowercase. `.mailmap` was present in cobra, jquery, libuv, nvm, rack: the numbers agree with the reference there, so blame output already carries the mapping.
- Compared: lines, lines-with-blank, commits per mail address. Result: commit counts agree on every repo; line counts agree except for the cases in the findings.
- git-fame 4.2.1 (venv/) was run (`-w -M -C -e --loc surviving`) on cobra, click, express, inspect, kilo, mux, plug. Totals match the tool on 4 of 7 (express, inspect, kilo, mux), but the per-author split differs by a few lines to a few hundred (express: <address> 12,823 vs 12,923). The tool equals plain git blame exactly in the same repos, so I attribute the git-fame spread to git-fame's own blame handling, not to the tool. I did not find the cause in git-fame and cannot rule out a flag difference on its side.
- Scripts: scripts/ (repos.txt, clone.sh, run_one.sh, ref.py, compare.py, fame.sh, merge_check.py, mktable.py, opts.sh, summary.py). Raw outputs: results/.

## Findings

1. **Crash on any repository with a git submodule that is not under a recognised vendor directory name** (high).
   - Repos: Tencent/rapidjson `24b5e7a8b2` (default run), square/okhttp `c3179301fc` (default), nvm-sh/nvm `b1b3a0038c` (default). With `--keep-generated`: jqlang/jq `49fbca1242` (`vendor/oniguruma`), google/leveldb `bb74ef7399` (`third_party/benchmark`), sharkdp/bat `a9aa73d215` (`assets/syntaxes/01_Packages`). In the default run jq, leveldb and bat survive only because their submodules sit under `vendor/`, `third_party/`, or are otherwise dropped before blame; that is luck, not handling.
   - Command: `node bin/surviving-lines.js --cwd repos/rapidjson -q` (exit 1).
   - Expected: submodule entries (mode 160000) skipped like binaries, run completes. Actual: `fatal: no such path thirdparty/gtest in HEAD`, no output, exit 1. The failing path is the gitlink.
   - Cause: `listTextFiles` (bin/surviving-lines.js:652-668) takes the file list from `git diff --numstat <empty-tree> <ref>`, which prints a gitlink as `1 0 <path>` (the "Subproject commit" line), so it passes as a one-line text file; `git blame` on it then fails. Workaround: `--exclude <submodule path>` (checked on rapidjson, which then runs: 45,917 lines).
2. **Binary or non-code files that `git diff --numstat` calls text are counted as source lines** (medium).
   - psf/requests `611c6162cb`: `ext/requests-logo.ai` (Illustrator/PDF stream) = 8,722 non-blank lines. Tool total 24,206 lines vs 15,532 with that file left out; `<address>` shows 9,963 lines vs 1,864, `<address>` 2,305 vs 1,732. Textualize/rich `9d8f9a372c`: `assets/logo.ai` 5,759 of 67,634 lines credited to willmcgugan (53,703 vs 47,995). colinhacks/zod `afdac65e0f`: four `*.ai` logos, about 4,600 lines credited to <address> (73,470 vs 68,849). BurntSushi/ripgrep `fada8f9386`: `tests/data/sherlock-nul.txt` (a file with NUL bytes beyond git's 8,000-byte probe, 2,133 lines) and `sherlock.br` (Brotli data) counted; jamslam 59,823 vs 58,312.
   - Command: `node bin/surviving-lines.js --cwd repos/requests -q --json`; compare `linesAttributed` 24,206 with the reference 15,532 (`python3 scripts/ref.py repos/requests out.json`). Expected: binary files skipped (README: "Binary files are skipped"). Actual: counted. `git ls-files --eol` reports these as `i/-text`.
   - Cause: binary detection is only the `-\t-` marker of `--numstat` (bin/surviving-lines.js:649-667), which uses git's diff heuristic (NUL in the first 8,000 bytes). Files that git itself treats as non-text elsewhere (`-text` in `ls-files --eol`, lone CR or late NUL) pass. Whether `.ai` files should be dropped is a convention choice, but a PDF/Brotli stream credited as hundreds of "lines of code" contradicts the stated rule. The 2-5 line differences in bubbletea (`*.golden` with escape bytes), gitignore, and others are the same class and small.
3. **Default `-C` makes runs very slow on mid-size repos** (medium, "slow case" criterion: over 60 s on a repo under 5,000 commits).
   - Alamofire/Alamofire `bda9ed57d7` (1,684 commits, 571 files): default run did not finish in 300 s (killed; 100 s limit also hit on a re-run), but `--no-copies` finishes in 13 s. Plain `git blame -w -M -C` over all files with 6 threads took 180 s by itself (scripts/ref.py), so the cost is git's, but the tool turns it on by default below 2,000 files. nlohmann/json `ffcd392be0` (5,373 commits): 168 s in the batch, 132 s alone; `--no-copies` 37 s. catchorg/Catch2 `0809213921` (4,831 commits): 100 s / 61 s alone; `--no-copies` 23 s. JamesNK/Newtonsoft.Json `52fa3aef1f`: 78 s.
   - Cause: `COPY_DETECTION_MAX_FILES = 2000` (bin/surviving-lines.js:32, used at :2330-2336) is a file-count threshold; blame -C cost depends on file size and history, not only file count. The tool does not warn that this will be slow, and `-q` hides progress.
   - Note: the `copyEffect` comparison (-C vs without) in the output suggests a second blame pass in some cases; I did not measure whether that doubles the cost (nlohmann raw run was 156 s, similar to the default, so probably not on every run).
4. **Bots whose names do not match the `[bot]` / noreply patterns are credited as people** (medium).
   - jekyll/jekyll `97c3bdc822`: `jekyllbot <<address>>` 1,697 commits and 1,513 lines, `jekyllbot <<address>>` 38 commits and 208 lines. vuejs/vue `9e88707940`: `vue-bot <<address>>` 113 commits. `StepSecurity Bot <<address>>`: 56 lines in bats-core, 157 in nlohmann/json, 1 commit in fmt. sinatra: `ReadmeCritic <<address>>` 15 commits (also in awesome, art-of-command-line). colinhacks/zod: `ZodBot <<address>>` 2 commits; bat: `Kira Security Bot`; logrus: `CodeLingo Bot`; express: `jade-bot`.
   - Command: default run, check the author table; expected: left out ("bots excluded") as dependabot is. Actual: listed as authors; in jekyll the bot has more commits than any human.
   - Cause: `isBotIdentity` (bin/surviving-lines.js:336) matches `[bot]` names and a fixed address list only; the README says "Nothing cleverer", so this is a stated limit. It misses the most obvious pattern, a name or local part ending in "bot". Whether to widen it is a product choice (the same pattern would hit real people, e.g. "Bot Hawkins"); I could not decide. `--include-bots` and `.mailmap` are the user's tools.
5. **Authors whose surviving lines are all blank have 0 in the "with blank" column** (low).
   - Seen in 40+ repos, e.g. cJSON `6d9f2443ab`: `<address>` has 14 blank lines alive; reference 14, tool row shows `linesWithBlank: 0`. The same author's commit count is right. Consequence: header "35,199 with blank lines" (detached click) disagrees with the bus factor line's "35,188 lines with blank lines" by the missing 11 lines; the with-blank bus-factor and shares use the smaller total.
   - Command: `node bin/surviving-lines.js --cwd repos/cJSON -q --json --keep-generated --no-detect-reformat --include-bots`, compare `authors[].linesWithBlank` with `git blame` (scripts/compare.py cJSON).
   - Cause: `withBlankOf` is filled for every address (:1093) but copied only onto entries of `authors` (:1144), which is built from non-blank counts, so blank-only addresses never get a row value; the commit-only row is created later with 0.
6. **A symlink is blamed as a one-line source file** (low, may be a deliberate convention).
   - hiredis `5bb7f030f6` (1 symlink, +1), urfave/cli (+1), clap (+12), bats-core (+10), jekyll (+9), zod (+4), gitignore (+3), swift-argument-parser (+2). `numstat` lists a symlink as one added line (its target path), and blame credits it to whoever committed the link. The README does not say symlinks are counted; I skipped them in the reference, so every difference of 1-12 lines in the comparison is explained by this. Not verified against intent.
7. **Observation, not a bug**: pallets/click `2247b35ea1` and flask: the commit "apply black" (93ba3ba, 1,619 surviving lines, David Lord) is reported under "mechanical rewrites checked ... not set aside" and still counted by default. This is the documented behaviour (only whitespace/quote commits are auto-ignored; the other candidates are listed with `--ignore-rev` advice). I could not decide whether "subject says black" should be excluded automatically.
8. **Observation, not a bug**: git-fame 4.2.1 per-author line counts differ slightly from the tool on 7 repos where the tool equals plain git exactly (see Method). The README says the two agree on its fixtures; on these real repos they do not, and I did not find the cause on git-fame's side.

## Not covered / limits

- Sweep stopped early on request. Not done: per-repo `--merge-identities` line-sum check against the ref (merge counts were only reviewed for wrongly merged people, not for every missed merge), git-fame on more than 7 repos, a repo with CRLF files and very long lines on purpose (Newtonsoft.Json and jquery contain some and match the reference), the 60 s criterion on idle hardware, `--sample` accuracy.
- Repos with no `.mailmap` were not tested for missed same-person merges beyond the groups reviewed; the "weak" suggestions the tool prints but does not merge were not judged.
- Timing: two repos ran in parallel with the CLI's 4 jobs each, so default-run seconds in the table are upper bounds (except F3 re-times).
